# 消息计数标记 + 未计数诊断

## 问题

11-23（rc.2 第一个完整日）出现 `raw 12 · kept 12 · msg 13` —— `msg > raw` 差 1 条。
候选原因有二，**从外部无法区分**：

1. 某条投递路径漏埋（代码缺陷）；
2. 其他会话仍在用升级前的插件实例（混版本），它们写消息但走旧计数。

只要无法归因，恒等式既不能证明对、也不能证明错，正式版就不敢发。

## 需求

- **R1 计数标记**：投递成功并计数后，给该 message 行写入 `rawSeq`（该日 `kept` 计数器的递增值）。
  - 每条进入投递管道的消息也应有 `rawSeq`（`raw` 序号）——两者二选一或都写，取能区分「未计数」的最小方案。
- **R2 未计数诊断**：`collab_index { action:"metrics" }` 每行追加 `uncounted N`：
  - `uncounted` = 当日 message 行里**没有计数标记**的条数（排除 `_r<n>`）；
  - 有 `uncounted > 0` 时，行尾标 `⚠未计数`，并在末尾给一句解释（旧版本写入 / 漏埋）。
- **R3 兼容**：老行没有标记 —— 属于「升级前写入」，计入 `uncounted` 但在说明里区分「早于 0.10.0」与「本版本缺标记」。
- **R4 工具数**：仍 **29**（不加工具）。

## 非目标

- 不修可能的漏埋路径（先归因，再决定修不修）。
- 不改 `raw/kept/msg` 的既有语义与计数时机。
- 不回溯历史行。

## 验收

- [ ] 正常投递 → message 行带 `rawSeq`；`uncounted = 0`；
- [ ] 手工写一条无标记的 message 行 → 该日 `uncounted = 1`，行尾 `⚠未计数`；
- [ ] `_r<n>` 重发行不计入 `uncounted`；
- [ ] 老数据（0.10.0 之前）→ 全部计入 `uncounted`，说明区分「早于 0.10.0」；
- [ ] 回归全绿；工具数 29。

## 变异

1. 投递时不写标记 → `uncounted` 断言必红；
2. 把 `_r<n>` 也计入 `uncounted` → 「重发不计入」断言必红。
